# Observing persistence in blockchain systems

**When blockchain resources have no expiry rule, what can we observe?**

The unit of study is a resource under a specific rule. Record the object, the authority or client applying the rule, the relevant observation date or height, what could change the object’s status and who can still access it. A block, a UTXO, a token balance, a contract entry and a network endpoint belong to different parts of the system. The same resource can be examined through several observational perspectives.

## Observations and coverage

| Resource or outcome | Candidate indicator and boundary | Starting evidence |
| --- | --- | --- |
| Growth of ledger history | Sum the byte length of serialized canonical blocks since a named height, divided by 10⁹ for GB. The result covers history added within the selected interval. Comparing total chain history requires a verified baseline. | Bitcoin heights 974,000–975,004, checked with parent hashes and three raw blocks. Daily block counts remain in the archive. A controlled Bitcoin node can reproduce the same sample with [getblock](https://bitcoincore.org/en/doc/30.0.0/rpc/blockchain/getblock/). |
| Spendable state | Count spendable UTXOs at the highest-height block assigned to a UTC day. For change over a selected interval, subtract the count on the first displayed date. | Daily Open Bitcoin Metrics UTXO counts. The source excludes provably unspendable outputs. Disk size and the age of outstanding UTXOs require their own observations. |
| Holdings and concentration | Measure supply or balances at a block. Calculate Gini from the underlying positive address balances. State the address population, threshold and treatment of custodians and contracts. | Coin Metrics funded addresses and current USDC supply on Ethereum. The general archive has metrics for other assets, including share at labelled exchange addresses for BTC and ETH. [Coin Metrics supply](https://docs.coinmetrics.io/network-data/network-data-overview/supply) |
| Dormancy and renewed movement | Compare the value of outputs spent during a day that were at least a given age with all output value spent on that day. To measure what is still dormant, take a separate UTXO age snapshot at a stated height. | Daily open Bitcoin spent-output values at thresholds of 365, 1,095, 1,825 and 3,650 days. The value is gross spent input value and includes self-transfers, change-related spending and consolidation. [Bitcoin transactions](https://developer.bitcoin.org/devguide/transactions.html) |
| State retention, renewal and restoration | For a live contract key, remaining TTL is last live ledger minus observed ledger. Measure live entries, archive transitions and restorations individually and document their storage class and protocol version. | Stellar TTL and age since last write are archived for two specific contract-instance keys. TTL snapshots alone do not identify the transitions. [Stellar state archival](https://developers.stellar.org/docs/learn/fundamentals/contract-development/storage/state-archival) |
| Node storage, connectivity and access | Measure disk use by component on a specified node and configuration. Probe the oldest retrievable block, endpoint success rate and latency against fixed requests. Study peer-session duration and off-chain link retrieval success separately. | Observed execution head is archived for supported endpoints. Bitcoin Core exposes a block-and-undo-files disk estimate and pruning fields. IPFS uses reachable providers and retention mechanisms such as pinning for content availability. [Bitcoin Core RPC](https://bitcoincore.org/en/doc/30.0.0/rpc/blockchain/getblockchaininfo/) · [IPFS persistence](https://docs.ipfs.tech/concepts/persistence/) |

For ordered positive address balances $b_i$ and population $n$, one reproducible Gini definition is $G = 2\sum_i i b_i / (n\sum_i b_i) - (n+1)/n$, with ranks starting at one. The population and denominator can change over time even when the formula stays fixed. A defensible measurement must publish the inclusion rules and coverage with each result.

Archive observations can show association. For effects attributable to an expiry or retention policy, a stronger starting point is a matched policy change in one protocol, or a controlled comparison of client configurations with the same chain height, workload and node specification. For example, the Ethereum Foundation documents partial removal of pre-Merge execution history. That provides a retention-policy comparison for disk and historical accessibility, with measurements by specific client and version. It does not establish effects on token holdings. [Ethereum Foundation announcement](https://blog.ethereum.org/2025/07/08/partial-history-exp)

## Interactive design

The resource-first design asks visitors to choose an object and a lifecycle stage. In the first implementation a reader looking for “how much history was added?” or “when did older BTC move?” would find prose and then need another navigation to see the associated archive series. A question-first design can place the measurement, its scope and its limitations in the same view. It better serves both of those tasks. Resource rules keep the lifecycle sequence for questions about the mechanism, especially Stellar archiving or differences between a node and a ledger.

In **Evidence**, each question has a named series, a detailed readout and a bounded set of controls relevant to the data. Choose a period, adjust the age threshold for spent outputs, and inspect a point with the keyboard, pointer or touch. Period changes update the chart, table and CSV together. URLs retain the selected controls and observation. The chart uses a zero reference. The state view also offers change relative to the window start to expose variation at smaller scales. Figures on this screen come from the listed snapshots.

In **Policy lab**, ten identical entries arrive each day for 84 days, with three entries read once per cohort at a chosen age. An entry expires once its age reaches its TTL. Expiry is applied before reads on the same day. A read of an archived entry restores it and restarts its TTL. An ordinary read leaves its TTL unchanged. A read of a removed entry fails. The three alternatives share one chart scale for active entries or missed reads. Each selected day shows active, archived and removed entries as well as cumulative reads and restorations. This is a synthetic policy comparison. It measures object counts and read outcomes within the workload. A node comparison would also need byte sizes, storage structure, latency, client and workload measurements.

These choices are based on task walkthroughs and browser validation. Future field evaluation should ask visitors to explain the distinction between UTXO age at spending and remaining idle stock, find the sampled period for a block-byte result, and predict which settings in the lab cause a missed read.

## Static datasets

| Versioned asset | Coverage and transformation | Source and reuse |
| --- | --- | --- |
| `bitcoin-bytes.v1.json` | 1,005 canonical Bitcoin blocks from height 974,000 through 975,004. Sum of 1,738,421,996 serialized bytes. The plot groups every 15 consecutive blocks and accumulates bytes from the start of the selected block range. | Public Bitcoin block facts retrieved from [mempool.space REST](https://mempool.space/docs/api/rest). Verify consecutive hashes and parent hashes. Check serialized byte count and double SHA-256 header hash at 974,000, 974,502 and 975,004 using [Blockstream Esplora](https://github.com/Blockstream/esplora/blob/master/API.md). The published file contains block facts and the verification records. |
| `bitcoin-utxo.v1.json` | 901 UTC days from 1 January 2024 to 19 June 2026. Count of spendable UTXOs after the highest-height block assigned to each day. | Diego R. Llanos, [Open Bitcoin Metrics v0.1.0](https://doi.org/10.5281/zenodo.21156871), `obm_utxo_eod_count_daily`, [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). |
| `bitcoin-spent-age.v1.json` | Same UTC window. Sum integral satoshi values from age bands at or above each threshold. The displayed share uses all spent-output value on the same date. The CSV preserves BTC to eight decimal places. | Diego R. Llanos, [Open Bitcoin Metrics v0.1.0](https://doi.org/10.5281/zenodo.21156871), `obm_spent_value_age_band_btc_daily`, [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/). The indexer defines a year as 365 days. |
| `ethereum-usdc.v1.json` | 180 UTC days from 27 May to 22 November 2026. Coin Metrics `AdrBalCnt` and `SplyCur` for `usdc_eth`. Supply precision stays intact in the source file and CSV. | [Coin Metrics Community](https://docs.coinmetrics.io/network-data/network-data-overview/supply), [CC BY-NC 4.0](https://creativecommons.org/licenses/by-nc/4.0/). |

The data preparation script uses provider responses saved locally, validates the pinned OBM release checksum, and checks the daily date grids. The time in `source.collectedAt` is the latest acquisition time of that snapshot’s source files on the build machine. Each row has its date or block height. Rebuilding from newly downloaded source files produces a new acquisition time. Publish changed windows or schema with a new versioned filename and update the UI reference.

These snapshots are served as static Cloudflare assets. The browser requests only the chosen study snapshot. The policy lab and resource rules require no data request. The CSV for an evidence view is generated from the displayed rows. The dynamic catalog, comparison and historical archive continue to use their existing API. Static series follow the coverage shown in the interface and refresh only with a new release.

### Additional source checks

Coin Metrics documents `BlkSizeByte`, `SplyAct1yr`, `SplyActPct1yr` and `SplyAdrTop100`. Keyless requests on 23 November 2026 found no Community coverage for these metrics. A direct Bitcoin `BlkSizeByte` series request returned HTTP 403. Open Bitcoin Metrics has a block-weight series, measured in weight units. A separate open UTXO dataset studied during source selection reported simulated expiry events and was excluded from empirical age observations. See [Coin Metrics block metrics](https://docs.coinmetrics.io/network-data/network-data-overview/network-usage/blocks) and [Organic Bitcoin dataset and model](https://github.com/organicbitcoin/obtc-utxo-data).
